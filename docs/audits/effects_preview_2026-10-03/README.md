# Effects preview audit — 2026-10-03

Phase 2 of `CHAIN_EFFECTS_PLAN.md`. The preview tool
(`src/dev_tools/effects_preview.py`) drives the live `EffectsRuntime`
through every reachable state and captures PNG frames so the aura +
takeover visuals can be reviewed without launching the full game.

Captures are grouped by motion mode. Both groups cover the same set of
states so a side-by-side diff shows exactly what reduced motion
suppresses.

Generated by:

```powershell
python src/dev_tools/effects_preview.py --capture
```

The capture runs headless under `SDL_VIDEODRIVER=dummy` and writes
PNGs into this directory (full motion) plus `reduced/` (reduced motion).

## Findings worth bringing back

1. **Particle anchor is hardcoded far from the quiz panel.** The
   captures make this obvious: on `chain_10_correct.png` the sparks
   bloom in the top-right at (1300, 100) — the anchor baked into
   `_Particle._ANCHOR_X / _ANCHOR_Y` — while the panel sits centered
   around (800, 470). This matches the Phase 1 open-question §10
   (`docs/design/effects_runtime_phase_1.md`): "The counter position
   actually depends on panel geometry; the handler should receive panel
   geometry via the snapshot. Phase 2's preview tool will make this
   visible." Confirmed. Phase 1 flagged this; Phase 2 can see it.
   Suggested fix path: have `main.Game.update` include the panel rect
   (or the counter rect specifically) in the snapshot, and have the
   handler re-anchor particles there in `_spawn_particles`.

2. **Residual particles survive a wrong-answer reset.** `chain_wrong.png`
   shows the lavender/pink Mythic sparks still drifting at the top-right
   after `chain → 0`. This is intentional (the particles drain over
   400–900 ms) but readers of the audit may misread it as a bug. Document
   this behaviour or add a visual cue (fast fade?) once the anchor fix
   lands and the sparks are centre-stage.

3. **Reduced-motion sample at 1500 ms shows an empty scene.** This is
   not a bug — the reduced mode's `shorten_to_ms: 900` dismisses the
   takeover before 1500 ms — but the frame is less informative than the
   other two samples. Consider capturing at 300 / 600 / 900 ms when
   reduced motion is active so all three frames show the takeover live.
   Deferred — not blocking.

4. **No performance surprises.** The capture pass renders 38 full HD
   frames in ~1 second. The particle pool never exceeded the configured
   budget during the forced-burst test (`test_particle_budget_cap`).

5. **Phase 3 (`identify_success_orb`) is already live.** The initial
   plan treated Phase 3 as a separate agent run after Phase 2. In this
   session, Phase 3 landed in parallel. The preview tool and tests were
   adapted to treat it as present-but-optional: lifecycle tests use
   `>=` on the handler set, and the `I` key / capture pass detect the
   handler at runtime. No change needed to `effects_runtime.py` or the
   handler files.
